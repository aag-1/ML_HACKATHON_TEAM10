# Decision log

Every design choice in PathSnap, who made it, and why. Each entry gives the options considered and the evidence behind the choice.
Phase 1 covers data preprocessing, feature engineering and model selection/training.

| ID | Decision | Chosen | Alternatives considered | Why |
|---|---|---|---|---|
| D1 | Project location | `~/Documents/Me/college/PathSnap` | temporary session folder | Durable; becomes the GitHub repo later. |
| D2 | Environment | `.venv` + pinned `requirements.txt` | uv, conda | Reproducible with plain Python on both demo laptops. |
| D3 | Problem framing | **Binary candidate scorer**: each (GPS point, nearby arc) pair is labelled true/false | Multiclass over arc IDs; learning-to-rank | Arc IDs are local to each trip (every trip has its own road network), so arc_id cannot be a class. A probability per candidate gives Top-1 (pick the best candidate), Candidate Miss Rate, Log Loss and Macro F1, and becomes the HMM emission in phase 2. |
| D4 | Per-point labels | **Monotonic DP alignment** of GPS points to the `.route` arc sequence | Nearest route arc | `.route` is a sequence of arcs, not one label per point. The DP only moves forward along the route, so loops and repeated arcs (trip 56 repeats 255 arcs) get the right occurrence. Self-check in `src/pathsnap/labels.py`. |
| D5 | Projection | **Per-trip UTM** (pyproj; zone from the trip's median position) | Local equirectangular; haversine | Trips are worldwide. UTM gives metres with under 0.1% distortion at trip scale, so point-to-segment distance and angles are valid. The brief rules out Euclidean distance in degrees. |
| D6 | Candidate generation | **Arcs within 50 m, keep the 10 nearest** | 100 m / 20; 30 m / 8 | Probe on student_test: true arc missed 1.5% at 25 m vs 0.1% at 50 m. Measured after building: miss rate 0.28% (train), 0.12% (student_test). Every remaining miss is caused by the 10-arc cap in dense networks. |
| D7 | Bad-label trips | **Trips 00000033 and 00000054 excluded from training** (kept in EDA). Points whose aligned label is more than 50 m from the GPS point are also dropped from training/evaluation. | Keep all; down-weight | Trip 33: the reference route is 122 m (median) from the GPS and 59% of labels are unreliable. Trip 54: median 140 m, 89% unreliable, and 85% of its GPS points have no road arc within 50 m (the GPS lies outside the supplied network). Training on these would teach wrong labels. |
| D8 | Stationary / duplicate points | **Kept**, with a `moving` flag (smoothed speed ≥ 1 m/s). A stopped car keeps its last moving heading. | Drop them | The brief needs a prediction for every observation. Heading is noise while stopped, so the model is told when that is the case. |
| D9 | Feature groups | **Geometry, Direction, Relative-to-others** (13 features) | + graph/context features | See `docs/02_features.md`. Direction separates two-way twins (A→B vs B→A share geometry; 76% of points have one). Relative features make values comparable across very different networks. Graph/context features are left for the HMM, which uses connectivity directly. |
| D10 | Validation | **5-fold GroupKFold by trip** on the 78 usable train trips | Leave-one-trip-out | Consecutive GPS points are almost identical, so a random row split would leak. Grouping keeps whole trips in one fold. Required by the brief ("group-aware"). |
| D11 | Primary selection metric | **Observation-level Top-1 accuracy**; log loss is the tie-breaker | Macro F1; log loss | Top-1 is what the API reports on demo day. Log loss measures probability quality, which matters because the probabilities become HMM emissions. |
| D12 | Class imbalance (≈15% positive rows) | **No resampling** | class_weight='balanced'; SMOTE | Keeps probabilities calibrated for the HMM. Top-1 is a per-point ranking, so the imbalance barely affects it. |
| D13 | Models (≥5) | **Logistic Regression, KNN (distance-weighted), Random Forest, HistGradientBoosting, MLP**, plus a no-training nearest-arc baseline | Gaussian NB, SVM-RBF, LightGBM/XGBoost | Covers linear, instance-based, bagging, boosting and neural families. All run in scikit-learn with no extra system libraries. SVM-RBF does not scale to ~1M rows. |
| D14 | Code layout | `src/pathsnap/` modules + numbered `scripts/` | Notebooks; both | The FastAPI backend in phase 2 imports the same preprocessing/feature code, so training and serving cannot drift apart. |
| D15 | Documentation | README + one doc per step + this log | One running log | Matches the report structure and the viva questions. |

## Fixed parameters (src/pathsnap/config.py)

| Parameter | Value | Reason |
|---|---|---|
| `HEADING_WINDOW` | ±2 points | Heading from displacement between points i−2 and i+2 smooths ~5 m GPS jitter at 1 Hz. |
| `MOVING_SPEED_MS` | 1.0 m/s | Below walking pace, GPS jitter dominates the displacement. |
| `SPEED_CLIP_MS` | 70 m/s | GPS jumps produce impossible speeds (up to 180 m/s observed). |
| `GAP_S` | 5 s | Nominal sampling is 1 s; above 5 s counts as a dropout (alignment may then jump ahead). |
| `ALIGN_MAX_STEP` | 15 arcs | Maximum route arcs a label may advance between consecutive 1–2 s points. Allows short arcs at speed. |
| `LABEL_MAX_DIST_M` | 50 m | Same as the candidate radius. A label farther than this cannot be a candidate and is treated as unreliable. |
| `SEED` | 42 | All randomness (RF, HGB, MLP, splits). |

## Phase 2

| ID | Decision | Chosen | Alternatives considered | Why |
|---|---|---|---|---|
| D16 | Final model | **HistGradientBoosting** | RandomForest, MLP | Statistically tied on CV Top-1 (0.8857 vs RF 0.8861, fold std 0.027) and equal test log loss (0.094). Trains 16× faster than RF (makes Bayesian optimisation practical). 180 KB model vs RF's 127 MB. See `docs/03_models.md`. |
| D17 | Bayesian optimisation | **Optuna TPE** (seed 42, 10 random warm-up trials) + MedianPruner, **40 trials**, maximise **CV Top-1** on the phase-1 folds; 6 parameters (learning_rate, max_leaf_nodes, min_samples_leaf, l2_regularization, max_features, max_bins), max_iter 1000 + early stopping | GP-based (Optuna GP, scikit-optimize); log-loss objective; 30/50/100 trials; 3-parameter space | TPE is a standard Bayesian method with a full trial record. The objective matches the selection metric, so tuned vs untuned compare like for like. Pruning spends compute on promising regions. |
| D18 | Accuracy target | **96–97% observation-level Top-1 (mandatory, set by the team)** | – | Classifier-only is ≈88%. The gap must come from the HMM/Viterbi sequence decoder (see error analysis in `docs/03_models.md`). |
| D19 | HMM emission | **Tuned-HGB probability**, log P weighted by a tuned exponent w | Gaussian on distance (Newson & Krumm); blend | Uses the selected model's outputs consistently (brief §8). Gives a clean classifier-only vs classifier+HMM comparison. |
| D20 | HMM transition | **Newson-Krumm on the directed graph**: exp(−\|d_road − d_gps\| / β), where d_road is the shortest directed path between the two projected positions | Topology-only (same / connected / other) | Respects one-way roads and travel direction, so a car cannot jump to the reverse twin without driving to a node and turning. Penalises detours in proportion to their length. |
| D21 | Gaps / unreachable transitions | **Split and restart**: a gap above a tuned threshold, no candidates, or no reachable transition ends the Viterbi segment and starts a new one | Bridge with a fixed penalty | A dropout or bad point cannot corrupt decisions elsewhere in the trip. Every point with candidates still gets a prediction. |
| D22 | Decoder parameter tuning | **Grid search on the 78 train trips using out-of-fold classifier probabilities**; student-test reported once | Tune on student-test | The classifier never saw the trips it scores during tuning, and student-test stays an honest estimate. |
| D23 | Label direction fix | Alignment cost = distance + **30 m × max(0, −cos(heading − arc bearing))** for moving points; label_dist and the 50 m reliability rule still use pure distance | Keep distance-only labels | When a route drives a road both ways, both directions are exactly equally close, so distance-only alignment was a tie. Phase-2 analysis found 80% of "wrong-direction" errors made while moving (>3 m/s) were label errors. Zero cost for arcs within 90° (turns unaffected) and for stationary points. Phase 1 was re-run on the corrected labels. Self-check in `labels.py`. |
| D24 | Bayesian optimisation budget | learning_rate **0.05–0.3**, max_iter **400**, early-stopping patience 10 (other 5 parameters unchanged) | Trip subsample; run overnight | With learning_rate down to 0.01, trials needed up to 1,000 rounds × 5 folds (≈20+ min each). The narrower range keeps 40 full-data trials to ~1–1.5 h. |
| D25 | Evaluator UI | **Single static HTML page + Leaflet**, served on laptop 2 with `python -m http.server` | Streamlit; React + Vite | Nothing to install or build on laptop 2; easy to explain. |
| D26 | UI content | **Map** (GPS points, HMM route, optional classifier-only layer) **+ metrics panel** (server-computed Top-1, classifier-only Top-1, continuity, points, segments, timings) | Map + accuracy only | Shows the classifier-only vs HMM comparison live. Ground truth never leaves the server. |
| D27 | Trip list / connection | **GET /trips** lists the trips in the server's evaluation folder (no hardcoded IDs); the UI has an API-address field remembered in the browser; the API listens on 0.0.0.0 with CORS | Hardcoded IDs + config file | Works with any 10 evaluator trips dropped into the folder; no file edits on demo day. |
| D28 | API logging | uvicorn access log **+ one pipeline line per request** (client, trip, points, candidates, segments, accuracy, ms per stage), also appended to `logs/api.log` | Access log only | The brief requires showing API logs on laptop 1; the summary line proves the full pipeline ran server-side. |
| D29 | Headline accuracy | **Strict observation-level Top-1** (exact directed arc, as defined in the brief), reported together with the binary candidate metrics (Macro F1, precision, recall, log loss). Correct-road (either direction) and driving-only Top-1 are reported as supporting diagnostics, clearly labelled. Team target: strict Top-1 ≥ 96%. | Correct-road or driving-only as headline | Matches the brief's definition. Diagnostics explain where errors come from: student-test preview strict 92.0%, correct road 96.3%, while driving 97.9% (83% of points). The gap sits in parked/crawling periods where the reference records one direction. |
| D30 | Decoder handling of parked / off-road periods | Two tuned options. **v_stationary:** when the ±10-point (≈20 s) speed is below this, backward drift along the same arc is jitter, costed as \|abs(Δ) − d_gps\| instead of reversing. **d_off:** if every candidate is farther than d_off and the car is slow (<3 m/s), the classifier evidence is down-weighted (×0.1). Both chosen on train OOF with beta, gap_s. | Leave decoder unchanged; speed-tempered emissions (short window) | Error analysis: long runs (1–7 min) of parked/crawling cars where 5–8 m GPS jitter reads as ~2 m/s. Each backward drift was charged as reversing, so Viterbi flipped to the reverse twin (whose drifts look forward). Train OOF Top-1: 92.65% → 93.25% in exploration. |
| D31 | Bayesian optimisation stopping point | **Concluded after 23 completed trials** (plus 9 pruned and 1 interrupted, 33 in total) instead of the planned 40 | Run all 40 | Team decision to save time. Gains had flattened: best CV Top-1 89.00% (trial 19) vs 88.86% untuned, with the last 13 trials not improving on it. Full record in `results/bayes_opt_trials.csv`. |
| D32 | Use of evaluator-test data | Pipeline **frozen first** (SHA-256 of artifacts + code in `results/frozen_pipeline_sha256.txt`), then the 10 evaluator trips run **once** through the API as a deployment check. Hashes re-verified afterwards; nothing tuned on these results. | Do not run until demo; run during development | The brief forbids using evaluator data for development. A single post-freeze run, provably unchanged, confirms the system works on all 10 demo trips without influencing any choice. Result: strict Top-1 94.75% (classifier-only 86.57%); 5/10 trips ≥ 96%. |
| D33 | Faster trip loading (speed only) | Each node's bounded road search runs once with a fixed range (1,150 m) and is cached; route reconstruction reuses it. The 1 km detour rule is unchanged. API adds `GET /summary` (evaluation-wide average, every trip run live and logged) and the UI shows it as a banner. | Cap detours at 200 m (faster, but changed 113 predictions on one trip, so rejected) | Shortest-path distances are exact, so outputs are identical: verified on all 10 student-test trips (predictions and routes). Total time for the 10 student-test trips 24.2 s → 15.2 s; the slowest trip 8.4 s → 4.6 s. Re-frozen hashes appended to `results/frozen_pipeline_sha256.txt`. |
